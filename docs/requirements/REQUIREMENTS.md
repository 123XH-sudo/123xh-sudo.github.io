## 1. 项目概述

### 1.1 项目名称

个人博客 RAG 智能问答系统开发与学习项目

### 1.2 项目背景

个人技术博客文章持续累积，传统关键词搜索语义理解能力弱，用户难以通过自然语言找到相关内容。本项目基于 LangGraph 从零搭建端到端 RAG 问答系统，支持语义检索与流式回答，同时以学习为导向系统掌握相关技术栈。

### 1.3 项目目标

| 目标类型 | 描述 |
| --- | --- |
| **功能目标** | 实现基于博客内容的智能问答，支持语义检索、引用溯源、流式输出 |
| **学习目标** | 理解 RAG 全链路原理，掌握 LangGraph 工作流编排及检索优化方法 |
| **工程目标** | 建立可维护、可增量更新、可部署的完整系统 |
| **内容目标** | 每个开发阶段产出对应技术博客，记录思考过程与踩坑经验 |

### 1.4 现有资产（基线）

以下为本仓库已有内容，后续开发在此基础上演进，而非从零开始：

| 资产 | 位置 | 现状 |
| --- | --- | --- |
| 博客数据源 | `_posts/*.md` | Jekyll Markdown，含 front matter |
| 分块脚本（初版） | `chunk_blog.py` | 按 `##` 标题分块，含元数据提取 |
| 聊天 Widget（初版） | `_includes/chat-widget.html` | 原生 JS + SSE，对接外部 API |
| Dify 知识库同步 | `.github/workflows/update-dify-kb.yml` | push 后增量上传变更文章 |
| 学习笔记 | `_posts/2026-08-06-RAG.md` 等 | RAG 原理、向量库、数据处理等 |

> **说明**：现有方案基于 Dify 外部服务；本项目目标是用 LangGraph + Chroma 自建完整 RAG 后端，逐步替换外部依赖。

## 2. 功能需求

### 2.1 知识库管理

| ID | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| F-KB-01 | 自动读取 `_posts/` 下 Markdown 文章 | P0 | 能解析 front matter，提取 title/date/tags |
| F-KB-02 | 支持递归分块策略 | P0 | chunk 大小可配置，保留标题层级上下文 |
| F-KB-03 | 使用 BGE-M3 生成 Embedding | P0 | 向量维度 1024，支持中文长文本 |
| F-KB-04 | 存储至 Chroma 向量库 | P0 | 支持持久化，重启后数据不丢失 |
| F-KB-05 | 增量更新机制 | P1 | 仅处理新增/变更文章，无需全量重建 |
| F-KB-06 | chunk 元数据完整 | P1 | 含 source_file、post_title、section_title、chunk_id |

### 2.2 检索系统

| ID | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| F-RE-01 | 向量语义检索 Top-K | P0 | 返回 K 个最相似 chunk，K 可配置 |
| F-RE-02 | Hybrid 检索（向量 + 关键词） | P1 | 提升专有名词、代码片段召回率 |
| F-RE-03 | BGE-Reranker 二次排序 | P0 | 对 Top-K 候选重排，提升 Top-3 命中率 |
| F-RE-04 | 检索结果引用溯源 | P0 | 返回来源文章标题、章节、相似度分数 |
| F-RE-05 | 自建评测集验证 | P1 | ≥20 条问答对，记录 Recall@K 指标 |

### 2.3 问答生成

| ID | 需求 | 优先级 | 验收标准 |

## 3. 非功能需求

### 3.1 性能指标

| 指标 | 目标值 | 测量方式 |
| --- | --- | --- |
| 检索延迟 | ≤ 500ms（本地 Chroma，≤100 chunk） | API 计时 |
| 首字延迟（TTFT） | ≤ 3s | SSE 首个 token 时间戳 |
| 索引增量更新 | ≤ 30s / 篇 | 单篇新增文章端到端耗时 |
| Recall@3 | ≥ 70%（自建评测集） | 人工标注 + 自动评估 |

### 3.2 用户体验

- 回答语言与用户提问语言一致（中文优先）
- 无法从知识库找到依据时，明确告知而非编造
- 引用来源可点击跳转至对应博客文章
- 加载/检索/生成过程有状态提示（如「检索中…」）

### 3.3 可维护性

- 代码含充分注释，关键模块有 docstring
- 每个功能模块独立提交，commit message 清晰
- 配置与代码分离（环境变量 / `.env`）
- 目录结构清晰，前后端分离

### 3.4 学习与文档

- 每个阶段完成后产出技术博客（含思考过程、选型理由、问题与解决方案）
- 每阶段结束进行知识点回顾与自测（面试题形式）
- 不强制独立编写全部代码，但须能读懂并解释实现原理

## 4. 边界条件与约束

### 4.1 范围内

- 数据源：本仓库 `_posts/` 目录下的 Markdown 博客文章
- 部署目标：个人服务器 / 本地开发环境（GitHub Pages 仅托管静态博客）
- 用户规模：个人使用，无需多租户、权限系统
- LLM：调用外部 API（DeepSeek 等），不在本地部署大模型

### 4.2 范围外

- PDF / Word 等非 Markdown 格式文档导入
- 多用户认证与对话历史持久化
- 生产级高可用集群部署（K8s、负载均衡等）
- 实时联网搜索（可作为 P2 扩展节点）

### 4.3 技术约束

- Python ≥ 3.10（类型注解、async 支持）
- Node.js ≥ 18（React 前端构建）
- Embedding / Reranker 模型本地推理（避免 Embedding API 费用）
- 向量库数据持久化至本地磁盘

### 4.4 依赖与风险

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| BGE 模型体积大，首次下载慢 | 环境搭建耗时 | 提供镜像源配置，文档说明缓存路径 |
| LLM API 限流/不可用 | 无法生成回答 | 多 Provider 降级，本地缓存常见问答 |
| 博客 chunk 过少导致检索稀疏 | 召回率低 | Hybrid 检索 + 降低 min_score 阈值 |
| 长文代码块被截断 | 回答质量下降 | 递归分块 + overlap + 代码块保护逻辑 |
