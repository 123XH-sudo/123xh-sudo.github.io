## 一、为什么需要查询优化

前几篇笔记里，我搭建的 RAG 系统已经能正常工作了：用户提问 → 向量检索 → 召回 chunk → LLM 生成回答。这个流程在用户输入精确问题时效果很好，但现实中用户的问题往往不是这样。

用我第一篇 RAG 笔记里提到的例子：

> 搜"怎么把项目放到服务器上"，它能找到标题为"部署指南"的文章。

用户说的是"放到服务器上"，文档写的是"部署"。字面不同，意思相同。向量检索在一定程度上能跨越这种语义差异，但当问题变得更加模糊时，差距就会暴露。

查询优化要解决的核心问题是：**把用户的口语化、模糊化、不完整的问题，转化为知识库能理解的检索查询。**

---

## 二、三种常见的查询问题

### 2.1 指代不明

多轮对话中，用户会使用代词指代前文提到的事物：

```
第 1 轮：RAG 的分块策略是什么？
第 2 轮：它有什么优缺点？
```

"它"指什么？检索系统单独看"它有什么优缺点"这句话，完全无法理解。

### 2.2 省略补全

用户省略了前文已经明确的信息：

```
第 1 轮：Docker 在项目中怎么用？
第 2 轮：那环境变量怎么配置？
```

"那"指的是 Docker 部署中的环境变量配置，但检索系统拿到的是"那环境变量怎么配置"，缺少关键上下文。

### 2.3 术语差异

用户用口语化表达，文档用书面术语：

| 用户输入 | 文档中的表述 |
|---------|------------|
| 怎么把项目放到服务器上 | 项目部署方法 |
| 怎么让容器自己重启 | Docker 容器自动重启配置 |

## 三、三种查询优化策略

### 3.1 查询改写（Query Rewriting）

**思路**：在知识检索之前，加一个 LLM 节点，让 LLM 结合对话历史，把用户的原始问题改写成更精确的检索查询。

**解决三个问题**：

- **指代消解**：把"它"替换为对话历史中明确提到的对象
- **省略补全**：把省略的成分补全为完整表述
- **术语标准化**：把口语化表达转为正式技术术语

**在 Dify 中的实现**：

```
用户输入 → LLM 改写节点 → 改写后的查询 → 知识检索 → LLM 生成回答
```

改写节点的 Prompt：

```
结合对话历史，将用户的问题改写为独立、完整、明确的检索查询。

用户输入：
{{#sys.query#}}

改写规则：
- 将指代词（它、这个、那个、其）替换为对话历史中明确提到的对象
- 将省略成分补全为完整表述
- 保持原意，不添加额外信息
- 只输出改写后的查询，不要输出任何解释

改写后的查询：
```

**关键约束**：改写后的查询必须忠实于用户原意，不能添加用户没问的信息。如果用户问"怎么部署"，不能改写成"怎么用 Docker 部署"——用户可能想用其他方式。

**实验结果**：

我在 Dify 中对比了开启和关闭查询改写的效果。三项测试中，只有一项体现了差异：

| 测试 | 改写前 | 改写后 |
|------|--------|--------|
| "它有什么优缺点" | LLM 凭空编造了一套分块策略的优缺点 | LLM 诚实回答"知识库中没有相关内容" |
| "那环境变量怎么配置" | 正确回答 | 正确回答（无差异） |
| "怎么把项目放到服务器上" | 正确回答 | 正确回答（无差异） |

**核心发现**：查询改写的首要价值不是"答得更好"，而是**防止 LLM 编造答案**。当用户输入包含指代词时，不加改写会导致检索系统抓到不相关的 chunk，LLM 拿到这些不相关的文本后仍然会"有问必答"，从而生成不实内容。改写后，指代词被替换为具体对象，检索命中正确的 chunk，LLM 能准确判断知识库中是否有相关内容。

### 3.2 HyDE（Hypothetical Document Embeddings）

**全称**：**Hy**pothetical **D**ocument **E**mbeddings，即"假设文档嵌入"。

**思路**：用户问一个问题，先让 LLM 凭空写一段"假设的回答"，再把这段假设回答转成向量去检索知识库。

**流程**：

```
用户输入 → LLM 生成假设回答 → Embedding → 检索知识库 → LLM 生成真实回答
```

**为什么有效**：

向量检索的本质是：把用户查询和知识库文档都转成向量，比较方向。但用户查询通常是口语化的短句，知识库文档是书面化的长段落，两者在措辞风格和语义密度上存在差异，导致向量匹配度下降。

HyDE 让 LLM 先生成一段书面化的假设回答作为中介，用风格相近的文本去匹配，命中率更高。

**举例**：

```
用户问："Redis 在项目中扮演什么角色"

LLM 生成的假设回答：
"Redis 在这个项目中主要承担两个角色：一是作为缓存层，
加速数据库查询；二是作为 Bull 任务队列的后端存储，
管理异步任务的调度和状态。同时 Redis 还可以用于会话管理..."

这段假设回答的词频、结构和术语密度，与真实文档更接近。
```

**代价**：多一次 LLM 调用，延迟翻倍，费用增加。如果 LLM 生成的假设回答包含事实错误，还会把检索引向错误方向。

### 3.3 Multi-Query 检索

**思路**：用户一个问题，让 LLM 生成 N 个不同角度的查询变体，分别检索后合并去重。

**流程**：

```
用户输入 → LLM 生成多个查询变体 → 并行检索 → 合并去重 → LLM 生成回答
```

**举例**：

```
用户问："Redis 在项目中扮演什么角色"

LLM 生成 3 个查询变体：
  1. "Redis 缓存和会话管理"
  2. "Redis 异步任务队列 Bull"
  3. "Redis 在 NestJS 项目中的应用"
```

**适用场景**：一个问题答案分散在多篇文章中，单一查询只能命中部分内容。

**代价**：N 次检索调用，延迟和费用成倍增加，还需要处理去重逻辑。

## 四、三种策略对比

| 策略 | 核心思路 | 解决的问题 | 代价 | 适用场景 |
|------|---------|-----------|------|---------|
| 查询改写 | 消歧 + 补全 + 标准化 | 用户表达不精确 | 低（一次 LLM 调用） | 多轮对话、模糊问题 |
| HyDE | 生成假设回答做桥梁 | 查询和文档的篇幅/措辞差异 | 高（多一次 LLM 调用） | 开放式问题、长文档 |
| Multi-Query | 多角度并行检索 | 答案分散在多个文档 | 高（N 次检索 + 合并） | 覆盖面问题 |

---

## 五、总结

查询优化是 RAG 系统中连接"用户"和"知识库"的关键环节。三种策略各有侧重：

- **查询改写**是基础，解决用户表达不精确的问题，性价比最高
- **HyDE** 通过生成假设回答跨越查询与文档之间的语义鸿沟
- **Multi-Query** 通过多角度检索扩大覆盖面

在实际项目中，策略选择取决于知识库规模和用户场景。小规模知识库中，查询改写的基础功能已经能覆盖大部分需求；随着知识库规模增长，可以根据具体的检索短板逐步引入 HyDE 和 Multi-Query。

---

## 个人思考

实验发现查询改写最核心的价值不是"答得更好"，而是**防止 LLM 乱编**。当用户说"它有什么优缺点"，不加改写时检索系统不知道"它"是谁，LLM 拿到不相关的 chunk 也会编一套答案。加了改写后，LLM 能准确判断知识库中是否有相关内容。先保证不乱说，再考虑说得好不好。

HyDE 和 Multi-Query 我没做实验。不是不想做，而是我的博客只有 5 篇文章，最基础的优化就足够了。这个判断来自前三个阶段的踩坑经验——换了三次 Embedding 模型、反复调了 Score 阈值，最终发现大部分参数在小规模下根本没有区别。与其把时间花在看不到效果的优化上，不如把最基础的查询改写做好。
