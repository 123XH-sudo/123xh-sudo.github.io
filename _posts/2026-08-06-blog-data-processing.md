## 1. 为什么要处理数据

RAG 系统的检索质量，90% 取决于数据质量。你喂什么，它就答什么。如果数据不干净，后续的检索模型、生成模型再强也无济于事。

## 2. Front Matter 剥离

博客文章开头有一段 YAML 配置信息（Jekyll 的 front matter），包含 `layout`、`date`、`tags` 等元数据。这部分是给静态站点生成器用的，不是文章正文内容。

如果不剥离，直接把整篇文章扔进知识库，用户搜"RAG"时可能检索到 `layout: single` 这种无意义片段，污染检索准确率。

但剥离不等于扔掉。front matter 中的 `title`、`date`、`tags` 等信息是有价值的——它们可以作为 chunk 的元数据标签，帮助后续检索时按分类过滤、按时间排序，以及实现引用溯源。

**正确做法**：解析 front matter → 提取元数据存到 chunk 的属性里 → 只将正文部分存入知识库。

## 3. 实践：用 Python 脚本实现按标题分块

抛开理论，我写了一个分块脚本来实际处理博客文件。

### 3.1 提取 front matter

```python
def parse_front_matter(text: str) -> tuple[dict, str]:
    match = re.match(r'^---\s*\n(.*?)\n---\s*\n', text, re.DOTALL)
    if not match:
        return {}, text
    metadata = yaml.safe_load(match.group(1)) or {}
    body = text[match.end():]
    return metadata, body
```

这段代码用正则表达式匹配两个 `---` 之间的内容，`re.DOTALL` 让 `.` 能够匹配换行符，确保跨行的 front matter 也能被正确提取。匹配到后，用 `yaml.safe_load` 解析为 Python 字典（含 title、date、tags 等字段），剩下的正文部分单独返回，用于后续分块。

### 3.2 按二级标题切分

```python
def split_by_heading(body: str) -> list[dict]:
    sections = re.split(r'\n(?=## )', body)
    chunks = []
    for section in sections:
        section = section.strip()
        if not section:
            continue
        title_match = re.match(r'^## (.+)', section)
        section_title = title_match.group(1).strip() if title_match else "（无标题）"
        chunks.append({
            "section_title": section_title,
            "content": section,
            "char_count": len(section),
        })
    return chunks
```

`re.split(r'\n(?=## )', body)` 在 `## ` 前面切分，同时保留 `##` 本身。每个切分出的 section 提取标题、计算字数，打包成 chunk 字典。

### 3.3 挂载元数据

每个 chunk 附上 5 个属性：来源文件名、文章标题、日期、标签、唯一 chunk_id。这些元数据将来在检索时可以实现按分类过滤、按时间排序，以及引用溯源——告诉用户"这个回答来自《某某文章》（发布于某日）"。

## 4. 分块大小的取舍

分块太小或太大都不行：

- **太小**（如 72 字的占位符内容）：提供不了有效信息，LLM 无法基于它生成有用的回答，白白浪费一次检索机会。
- **太大**（如 2548 字的巨型 chunk）：包含多个子话题，用户问"SSL 证书怎么申请"时，LLM 被迫读完大量无关内容，既浪费 token 又降低准确率。而且巨型 chunk 的向量表示会被不相关内容稀释，导致语义匹配精度下降。

我的实践方案是按 `##` 标题层级切分，每个标题下是一个语义完整的段落单元，兼顾了完整性和粒度。对于博客这种 Markdown 格式的内容，标题本身就是天然的语义边界。

## 5. 代码块与上下文

代码块和解释文字必须放在同一个 chunk 里。如果分开，LLM 检索到一段纯代码时无法理解它的业务意图和使用场景。

比如一段 `docker run` 命令，脱离了上下文：

- LLM 不知道这是在部署什么服务
- 不知道每个参数的含义
- 不知道这是开发环境还是生产环境配置

只有解释文字和代码一起出现，LLM 才能准确理解：这段代码是做什么的、为什么这样写、在什么场景下使用。

## 6. 脚本运行结果与发现的问题

运行脚本后，4 篇文章生成了 48 个 chunk，发现了两个实际问题：

**无标题 chunk**：部分文章开头有总述段落，在第一个 `##` 标题之前，导致 chunk 标题为"（无标题）"。解决方案：如果内容较短（< 200 字），直接丢弃；如果内容较长，合并到第一个 `##` 标题的 chunk 中，让它拥有上下文归属。

**占位符内容**：模板文章中出现了 `## 大章节1 ### 小节1.1` 这类模板占位符，内容不足 50 字且无实质信息。这类 chunk 需要按规则过滤——检测到内容过短且包含模板标记时直接丢弃，避免污染知识库。

## 7. Dify 平台实践：创建知识库

本地脚本验证了分块逻辑后，下一步是上 Dify 平台实际操作。

### 7.1 创建步骤

1. 打开 Dify，侧边栏找到「知识库」，点击「创建即用型知识库」
2. 选择数据源，导入 `_posts/` 文件夹中的全部博客文件
3. 进入「文本分段与清洗」设置，分段标识符输入 `##`（按二级标题切分），分段最大长度 1000，分段重叠长度 150
4. 索引方式选择「高质量」，Embedding 模型选择 `text-embedding-3-small`
5. 检索设置选择「混合检索」，开启 Rerank 模型，TopK 设为 3，Score 阈值设为 0.3

### 7.2 关键参数说明

| 参数 | 含义 | 我的设置 |
|------|------|---------|
| 分段标识符 | 按什么符号切分文本 | `##`（按二级标题边界切分） |
| 分段最大长度 | 单个 chunk 的字数上限 | 1000（超过则在此范围内进一步切分） |
| 分段重叠长度 | 相邻 chunk 之间重叠的字数 | 150（防止关键信息卡在边界被切断） |
| Rerank 模型 | 对检索结果二次排序，按语义匹配度重排 | 开启（提升检索精度） |
| TopK | 取匹配度最高的前 N 个 chunk | 3（太少漏信息，太多塞无关内容） |
| Score 阈值 | 相似度低于此值的 chunk 被丢弃 | 0.3（过滤掉完全不相关的结果） |

Rerank 模型的工作原理：先用向量检索召回一批候选 chunk，然后用更强大的交叉编码器对它们重新打分排序，确保最相关的内容排在前面。TopK=3 意味着最终取前 3 个最匹配的 chunk 喂给 LLM。

## 8. 关键踩坑：分段标识符 vs Embedding 模型

创建知识库时，我习惯性地把分段标识符设成了 `\n`（按换行符切分），上线后发现大量问题回答不了，"怎么部署 New API"完全检索不到。

一开始怀疑是 Embedding 模型不适合中文，于是接连切换了三个模型：`text-embedding-ada-002` → `bge-large-zh` → `text-embedding-3-small`。结果换了模型依然检索不到，才意识到问题不在模型上。

**真正的根因是分段标识符 `\n`**。按换行符切分会把一篇文章切成大量碎片——一个段落一个 chunk，语义被打散，向量表示丢失了上下文关联。改成 `##` 按标题切分后，每个 chunk 是一个完整的语义单元，检索精度立刻大幅提升。

**这个经验很重要**：RAG 系统出问题时，优先怀疑数据分块方式，而不是 Embedding 模型。对于中文博客而言，如果内容本身是中文主导，主流 Embedding 模型之间的差异远小于分块策略的差异。

## 9. Dify 自动分块 vs 本地脚本分块

| 维度 | Dify 默认（固定 500 字） | Dify 优化后（`##` 切分） | 本地脚本（`##` 切分） |
|------|------------------------|------------------------|---------------------|
| 切分方式 | 按字数强制切分 | 按标题语义切分 | 按标题语义切分 |
| 语义完整性 | 差，可能截断论述 | 好，每个 chunk 自成单元 | 好，每个 chunk 自成单元 |
| 元数据支持 | 自动挂载文件名等 | 自动挂载文件名等 | 手动控制，可定制 |
| 检索精度 | 低，经常找不到答案 | 高，基本能准确回答 | —（本地不含检索） |

结论：按 `##` 标题切分显著优于固定字数切分。Dify 改造成本低，直接改分段标识符即可。本地脚本的优势在于可以自定义元数据字段和清洗规则，适合更复杂的场景。

## 10. 总结

这次实践从本地 Python 脚本到 Dify 平台，完整走通了博客数据处理的流程。三个核心原则：

1. **剥离元数据，但保留其价值**——front matter 不进入知识库，但作为 chunk 属性存储
2. **分块要适中**——太小无用，太大不精，标题层级是天然的好边界
3. **代码与上下文不可分离**——分开的代码块对 LLM 来说几乎等于无效信息

额外收获：**当 RAG 检索效果差时，先检查分块方式，再怀疑模型**。分段标识符从 `\n` 改成 `##`，比我换三次 Embedding 模型都管用。
