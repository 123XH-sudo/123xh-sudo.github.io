## 1. 为什么需要向量数据库

RAG 系统的核心操作是"找到和用户问题最相似的文档片段"。这个操作的本质是**向量相似度计算**——把文本转成高维向量，然后找距离最近的。

如果用传统数据库（如 MySQL）存储向量，查询时只能做全量扫描：把每一行的向量读出来，逐个计算相似度，再排序取 Top-K。这在数据量大的时候会非常慢——10 万条数据就要算 10 万次高维向量运算。

**向量数据库的核心优势**：通过索引结构（如 HNSW）快速定位最相似的向量，不用全量扫描。HNSW 的精髓是把向量组织成"分层公路网"——上层路少但快（粗略定位），下层路密但慢（精确匹配），检索时先走高速公路到大致区域，再走小巷找具体目标。从 O(n) 降到近似 O(log n)。

## 2. 主流向量数据库对比

| 数据库 | 类型 | 部署方式 | 适合谁 |
|--------|------|---------|--------|
| Chroma | 开源、轻量 | 嵌入 Python，本地运行 | 个人开发者、原型验证 |
| Milvus | 开源、分布式 | 独立服务，Docker/云 | 企业级大数据 |
| Pinecone | 闭源、SaaS | 仅云服务 | 不想管运维的团队 |
| Weaviate | 开源 | 自托管或云 | 需要内置向量化能力的 |
| Qdrant | 开源、Rust | Docker/云 | 追求高性能的中型项目 |
| pgvector | PostgreSQL 插件 | 装在 PG 里 | 已有 PG 不想加新组件 |

## 3. 我的选型：Chroma

我选择了 **Chroma**，原因很简单：

1. **开源且轻量**——不需要额外部署服务，Python 直接引入即可使用
2. **本地运行**——我的博客数据量小（几十篇文章），不需要分布式方案
3. **零配置**——创建 Collection、插入向量、检索，几行代码搞定

Chroma 对个人博客场景来说，就像 SQLite 对小型 Web 应用——够用、简单、没有运维负担。相比之下，Milvus 虽然功能强大，但需要独立 Docker 服务，对个人项目过于沉重；Pinecone 是云服务，需要额外的网络调用和费用。

## 4. 存储结构设计

向量数据库里存的不只是向量，还有描述数据的 metadata。我的设计如下：

```
Collection: my_blog
├── Document 1
│   ├── id: "chunk_001"
│   ├── content: "RAG是一种将信息检索与文本生成相结合..."
│   ├── vector: [0.23, -0.45, 0.78, ...]   ← 1536维向量
│   └── metadata: {
│         title: "RAG系统基础",
│         date: "2026-08-06",
│         categories: ["学习笔记"],
│         tags: ["RAG", "LLM"],
│         url: "/posts/2026-08-06-RAG"
│       }
├── Document 2
│   └── ...
```

metadata 中包含了标题、日期、分类、标签和原文链接。这些字段可以用于：
- **按时间过滤**：用户只想搜最近一年的文章
- **按分类过滤**：只搜「学习笔记」分类
- **引用溯源**：回答时附上原文链接

在实际检索时，通常是"先向量检索找 Top-K，再用 metadata 过滤不符合条件的"——两步走，兼顾语义匹配和条件筛选。

> **注**：当前 `chunk_blog.py` 脚本已提取 title、date、tags、source_file，但 categories 和 url 尚未实现（categories 存在于 front matter 中但未解析；url 需根据 source_file 拼接）。这在后续脚本迭代中补上。

## 5. 检索方式对比实验

我在 Dify 上对三种检索方式做了对比测试，使用同一个问题"怎么部署 New API"和"如何安装环境"：

| 检索方式 | 原理 | New API 部署结果 | 环境安装结果 |
|---------|------|-----------------|-------------|
| **纯向量检索** | 语义匹配，理解"意思" | ⭐⭐⭐ 5 步完整步骤 + Docker 命令 | ⭐⭐⭐ 完整 |
| **纯全文检索** | 关键词精确匹配 | ⭐⭐⭐ 5 步完整步骤 + Docker 命令 | ⭐⭐⭐ 完整 |
| **混合检索** | 向量 + 全文加权合并 | ⭐⭐ 只提到章节存在，未给出步骤 | ⭐⭐⭐ 完整 |

### 为什么混合检索反而不如纯向量？

这个结果最初让我意外——混合检索号称"两者互补"，结果却最差。

推测原因：我的博客里多篇文章共享技术术语（Docker、Nginx、MySQL）。用户搜"怎么部署 New API"时，全文检索可能匹配到其他文章里包含"Docker"的 chunk（比如学习日记中的 Docker 内容），这些候选挤占了 TopK 位置，把真正相关的 New API 部署章节排下去了。由于 Dify 预览区不展示每个 chunk 的检索分数，这目前只是推测，后续需要进一步验证。

而纯向量检索理解的是整体语义——"部署 New API"和《New API 部署指南》在语义上高度相似，不受共享术语的干扰。

### 结论

对于技术博客这种术语密集、语义边界清晰的场景，**纯向量检索效果最好**。混合检索更适合知识库中术语分散、需要关键词兜底的场景（如公司内部文档，包含人名、工号等专有名词）。

### TopK 参数调优实验

随后我固定纯向量检索，调整 TopK 参数测试它对回答质量的影响。使用问题"我的学习日记里提到了哪些技术栈？"：

| TopK | 检索到的内容 | 回答质量 |
|------|------------|---------|
| K=1 | 同一篇文章里的"服务器环境准备"（Nginx、MySQL、Redis） | ❌ 完全错误 |
| K=3 | 找到了文章末尾的"学习心得总结"表格（NestJS、React Flow、Langchain、Bull） | ✅ 正确 |
| K=5 | 结果与 K=3 相同 | ✅ 正确 |

**关键发现**：TopK=1 只取了相似度最高但内容错误的 chunk，而正确答案排在第 2-3 位。这说明 TopK 太小时，如果向量模型判断"更相似"的 chunk 恰好不是你想要的，正确答案就没有机会被选中。TopK=3 给了正确答案被召回的空间。

但 TopK 也不是越大越好——K=5 和 K=3 结果一致，多余的 chunk 没有带来额外价值，反而增加了 token 消耗。对于我的博客场景，**TopK=3 是最佳平衡点**。

### Score 阈值实验

我测试了 Score 阈值对检索的影响。固定 TopK=3、纯向量检索，使用两个不同问题：

**问题一**："RAG 的分块策略是什么"

| Score 阈值 | 结果 |
|-----------|------|
| 0.1 | 完整准确 |
| 0.3 | 完整准确 |
| 0.7 | 完整准确 |

这个问题的相关 chunk 匹配度极高，阈值怎么调都不影响结果。这说明如果问题本身高度匹配，阈值不起作用——**阈值只拦"边缘候选"，不拦"核心答案"**。

**问题二**："Redis 在整个项目中扮演什么角色"

这个问题更狡猾：Redis 在知识库里出现在两个地方——New API 部署表格（简单提了一句"缓存和会话管理"）和学习日记（Bull+Redis 异步任务详细章节）。前者匹配度低，后者匹配度高。

| Score 阈值 | 结果 |
|-----------|------|
| 0.1 | 包含部署组件 + 异步队列 + 实时推送 |
| 0.3 | 同上 |
| 0.5 | 同上 |
| 0.7 | 同上 |

四个阈值结果依然一致。即使分值较低的"部署组件"那部分，其相似度分数也足以通过 0.7 的阈值。

**结论**：在 5 篇文档的小规模知识库中，Score 阈值几乎没有可见影响。原因有二：(1) 文档量太少，候选 chunk 总数有限，不存在大量低分噪音；(2) 所有文章话题相近，即使是"弱匹配"分数也不低。Score 阈值的真正价值体现在数百篇乃至数千篇文档的大知识库中——那时候低分噪音数量庞大，没有阈值过滤，LLM 上下文会被垃圾信息淹没。

## 6. 三个核心概念澄清

### Embedding ≠ 向量

- **Embedding**（嵌入）是过程：把文字映射为向量的方法
- **向量**（Vector）是结果：映射后得到的高维数字数组

日常说"把这段文字做 embedding"意思就是"把它转成向量"。Dify 中 `text-embedding-3-small` 是 Embedding 模型的名字。

### HNSW 索引原理

Hierarchical Navigable Small World（分层可导航小世界）是目前最主流的向量索引算法。它把向量组织成多层图结构——上层连接稀疏但覆盖广（像高速公路），下层连接密集但范围小（像小巷）。检索时从顶层快速定位大致区域，逐层下降到精确匹配，避免了全量扫描。

### 向量数据库 vs 传统数据库：互补而非替代

向量数据库强于语义相似度检索，但事务和关联查询弱；MySQL 反之。实际 RAG 系统中两者通常结合使用：向量库存 chunk 向量 + metadata 做检索，关系型数据库存文章原始信息做管理和展示。

> **注**：Dify 封装了底层向量数据库（社区版默认使用 Weaviate），用户在平台上操作时无需关心具体实现，但理解其底层原理有助于排查问题和优化性能。

## 7. 总结

学到的核心认知：

1. **向量数据库的价值在于"索引加速"**，不是全量扫描
2. **选型要匹配场景**——个人博客用 Chroma，企业大数据用 Milvus，不想管运维用 Pinecone
3. **metadata 设计决定了检索的灵活性**——至少包含标题、日期、分类、链接
4. **检索方式没有银弹**——术语密集的技术博客场景，纯向量检索比混合检索更稳定
5. **TopK 是安全网**——K=1 容易漏掉正确答案，K=3 给了"排名靠后但内容正确"的 chunk 被召回的机会
6. **Score 阈值在小知识库中影响有限**——5 篇文档时分值天然悬殊，阈值的主要价值在知识库变大后才体现

这次实践让我明白了一个关键原则：**RAG 的每个组件选择都没有绝对的最优解，必须根据具体场景反复实验验证。**
