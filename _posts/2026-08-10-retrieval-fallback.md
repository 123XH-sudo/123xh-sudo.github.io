## 一、前情回顾

前两篇笔记中，我依次完成了：

1. **相似度计算**：理解向量、余弦相似度、归一化等基础概念
2. **查询优化**：在知识检索前加入 LLM 改写节点，解决指代消解问题

现在 Dify 中的 Chatflow 是这样的：

```
用户输入 → 查询改写 → 知识检索 → LLM 生成回答
```

这个流程在用户问题属于知识库范围内时效果很好，但有一个明显的漏洞：**如果用户问了一个博客中没有的内容，系统会怎么处理？**

---

## 二、对话历史管理

### 2.1 记忆的本质

在 Dify 中开启"记忆"功能后，底层做的事情是：**把最近 N 轮对话拼接成一段文本，塞进 LLM 的上下文窗口。**

LLM 实际收到的上下文包括：

```
[系统 Prompt]
[对话历史]：最近 N 轮的问答
[当前用户输入]
[检索到的知识库内容]
```

每个部分都在消耗 LLM 的上下文窗口。对于 8K 上下文窗口的模型，通常够用；但当知识库扩大、检索到的 chunk 增多时，对话历史占用越多，留给检索结果的空间就越少。

### 2.2 记忆窗口大小

窗口大小决定保留多少轮历史对话：

| 窗口大小 | 优势 | 劣势 |
|---------|------|------|
| 3 轮 | 话题切换时不干扰 | 跨轮指代可能丢失 |
| 5 轮 | 平衡历史记忆和上下文预算 | 长对话中仍可能丢失 |
| 10 轮 | 跨轮指代都能覆盖 | 话题切换后旧信息干扰 |

个人博客助手场景中，用户通常不会连续问超过 5 轮，5 轮左右是一个比较合适的窗口。

## 三、检索置信度判断

### 3.1 Score 阈值的盲区

在模块一中我学过，余弦相似度看的是向量方向是否一致。但方向接近不等于内容相关。

举个例：用户问"RAG 分块策略有什么优缺点"，两个 chunk 分别是：

- Chunk A："RAG 分块是 RAG 系统中的关键步骤。分块策略决定了..."
- Chunk B："分块策略的优势在于保持了语义完整性。缺点是需要..."

两个 chunk 的向量方向和用户查询都很接近，Score 可能差不多。但 Chunk A 只是背景介绍，没有提到优缺点。Score 区分不了这两者。

这是因为 Embedding 模型做的是**语义相似度**，不是"问答匹配度"。一段文字和问题语义相关，不代表它回答了问题。

### 3.2 更可靠的方案：LLM 判断

在检索之后、生成之前，加一个 LLM 判断节点，让 LLM 逐字阅读每个 chunk，判断是否真的回答了问题：

```
检索到的 chunk → LLM 判断 → 条件分支
                              ├─ 是 → 正常生成回答
                              └─ 否 → 触发回退
```

这本质上就是 Rerank 的思路，只是判断标准更明确——不是看"相关度"，而是看"是否回答了问题"。

## 四、回退策略设计

### 4.1 为什么需要回退

当用户问到知识库中不包含的内容时，不加回退的 LLM 会怎么做？我在模块二的实验中已经看到了答案：**LLM 会凭空编造**。

不加查询改写时，用户问"它有什么优缺点"，检索系统抓到了不相关的 chunk，LLM 拿着这些内容，硬是编了一套"分块策略的优缺点"。这不是它想骗人，而是它的设计就是"有问必答"。

回退策略的作用就是：**当系统无法找到可靠答案时，诚实告知用户，而不是编造。**

### 4.2 三级回退

根据检索质量，可以把回退分为三级：

**一级回退：降低阈值重新检索**

当检索结果偏少或 Score 偏低时，降低阈值或增大 TopK 再试一次。可能捞回之前被过滤掉的内容。

```
第 1 次：TopK=3, Score=0.3 → 只有 1 个 chunk 超过阈值
第 2 次：TopK=5, Score=0.15 → 召回 4 个 chunk
```

**二级回退：LLM 自身知识兜底 + 标注**

```text
"根据我的博客内容，没有找到相关记录。
以下是我基于通用知识的回答：
...
[注：以上内容并非来自博客知识库]"
```

**三级回退：主动引导用户**

"抱歉，我暂时无法回答这个问题。建议你换个关键词重新提问。"

### 4.3 避免死循环

最需要避免的情况：用户问 → 回退追问 → 用户再问 → 还是回退 → 再追问 ... 这种死循环会让用户极其烦躁。

解决方式：设置回退次数上限。同一轮对话中连续触发回退超过 2 次，直接走三级回退，引导用户换方向。

## 五、在 Dify 中的实现

### 5.1 完整 Chatflow

结合模块二和模块三，我的 Chatflow 最终形态：

```
用户输入
  → 查询改写（LLM 节点）
  → 知识检索（TopK=3, Score=0.3）
  → 条件分支
      ├─ 检索结果为空 → 回退 LLM 节点
      └─ 检索结果不为空 → 正常 LLM 生成回答
```

### 5.2 条件分支的实现

在 Dify 中，条件分支节点判断知识检索结果是否为空的条件是：

```
{{#知识检索节点.result#}} is empty
```

- IF 分支（结果为空）：连接到回退 LLM 节点
- ELSE 分支（结果不为空）：连接到正常 LLM 生成节点

### 5.3 回退 LLM 的 Prompt

```
知识库中没有找到与用户问题相关的信息。

用户问题：{{#sys.query#}}

请诚实告知用户：博客中暂时没有覆盖这个问题。
如果问题在你自身知识范围内，可以简要回答，
但必须标注"以下内容并非来自博客知识库"。
```

### 5.4 测试结果

| 测试问题 | 是否触发回退 | 回答质量 |
|---------|------------|---------|
| "Python 怎么爬虫" | 是 | 诚实告知"知识库中没有相关信息" |
| "RAG 的分块策略是什么" | 否 | 正常回答，内容正确 |

两个分支都正常工作，回退路径和正常路径互不干扰。

## 六、总结

多轮检索与回退策略是 RAG 系统的"安全网"。它解决的不是"如何答得更好"，而是"在无法回答时如何体面地退出"。

核心要点：

1. **对话历史管理**本质是上下文预算的分配问题
2. **Score 阈值**挡不住"方向接近但内容无关"的 chunk，需要 LLM 做二次判断
3. **回退策略**分三级，按场景选择
4. **避免死循环**，设置回退次数上限

结合前三个模块，阶段四的检索策略学习到此完成。当前 Chatflow 已经能覆盖：查询改写（解决指代问题）、向量检索（找到相关 chunk）、条件回退（应对知识盲区）三个核心环节。

---

## 个人思考

搭完回退策略后，我发现一个有意思的事：我的系统 Prompt 其实已经写了"如果没有相关信息，请明确告知用户"，所以回退分支和正常分支的效果几乎一样。这不是回退机制鸡肋，而是我从一开始就写了一个好 Prompt，把"不乱说"这个底线兜住了。

回退策略的真正价值在于可扩展性：一级回退（降低阈值重试）、二级回退（LLM 自身知识兜底 + 标注"非博客来源"），这些是 Prompt 里一句话搞不定的。而且如果你没有一开始就写好 Prompt，回退就是防止 LLM 胡说八道的最后防线。

回顾整个阶段四，最有成就感的是从零搭建一个知识库，然后能检索到相关内容并回答问题。最让我意外的是，很多优化在小规模场景下根本看不出效果——不是不需要，而是不到时候。
